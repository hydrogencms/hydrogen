# Choosing modules

A Hydrogen project is the core plus the modules it compiles in: the database adapter, pages, the website
renderer, images, search engines and anything third parties publish. The list lives in `hydrogen.yaml` at the
project root, and the `hydrogen` CLI keeps `go.mod` and the wiring code in step with it.

```yaml
# Modules compiled into this project. Edit with `hydrogen add` / `hydrogen remove`, then `hydrogen generate`.
modules:
  - sqlite
  - postgres
  - images
  - github.com/acme/hydrogen-stripe        # third-party: a package with `func Module() kernel.Module`
```

An entry is a catalog name (below) or the Go package path of a third-party module. Order is kept as written (the
kernel orders modules by their `Requires` anyway). Unknown keys, unknown names, malformed paths and duplicates
fail with the file name. Versions are not written here: they live in `go.mod`.

## Commands

Run these in the project directory. Outside a project they fail, and `hydrogen modules` only lists the catalog.

| Command | Does |
| --- | --- |
| `hydrogen modules` | Lists the catalog; `*` marks the modules this project uses (third-party ones are listed after). |
| `hydrogen add <name\|path[@version]>…` | Adds modules to `hydrogen.yaml`, fixes `go.mod`, regenerates `modules_gen.go`, runs `go mod tidy`, and prints the module's docs page and config key. |
| `hydrogen remove <name\|path>…` | The reverse. A requirement is dropped by `go mod tidy` only when nothing else imports it. |
| `hydrogen build [-o path] [go build flags]` | Regenerates `modules_gen.go`, then `go build -trimpath` into `bin/<project dir name>` with `CGO_ENABLED=0` unless set. Other arguments go to `go build` (`-tags`, `-ldflags`); `GOOS` and `GOARCH` come from the environment. Prints the path, the size and the module list. |
| `hydrogen generate` | Also regenerates `modules_gen.go` from `hydrogen.yaml` (when the file exists) before generating typed code. |
| `hydrogen modules -versions` | Builds the project and runs its own `modules` command: the modules that are really compiled in, with their versions. |
| `hydrogen modules init <name\|path>…` | For a project that registers modules by hand: creates `hydrogen.yaml` and `modules_gen.go` (see below). |

`hydrogen dev` regenerates `modules_gen.go` whenever it rebuilds, so editing `hydrogen.yaml` while it runs
restarts the server with the new module set. Every command that changes files is all or nothing: the files are
written through temporary files, and when `go get` or `go mod tidy` fails, `hydrogen.yaml`, `modules_gen.go`,
`go.mod` and `go.sum` are put back as they were.

## The catalog

| Name | Package | Own Go module | Config key |
| --- | --- | --- | --- |
| `sqlite` | `github.com/hydrogencms/hydrogen/modules/sqlite` | yes | `database.url` |
| `postgres` | `github.com/hydrogencms/hydrogen/modules/postgres` | yes | `database.url` |
| `pages` | `.../modules/pages` | no | `modules.pages` |
| `site` | `.../modules/site` | no | `modules.site` |
| `overlays` | `.../modules/overlays` | no | none (see [locales](locales.md)) |
| `images` | `.../modules/images` | no | `modules.images` (see [images](images.md)) |
| `meilisearch` | `.../modules/meilisearch` | no | `modules.meilisearch` (see [meilisearch](meilisearch.md)) |

Modules in the core module need no `go.mod` change. The adapters are separate Go modules because of their
dependencies: `hydrogen add postgres` runs `go get` for them at the core's version. A project built with
`hydrogen new -core <checkout>` replaces the core with the local checkout; `add` then adds the matching
`replace <module> => <checkout>/modules/<name>` as well, and `remove` takes it away again.

## Generated wiring

`modules_gen.go` sits in the project's main package and registers the modules:

```go
// Code generated by hydrogen from hydrogen.yaml; DO NOT EDIT.
package main

import (
	"github.com/hydrogencms/hydrogen"
	"github.com/hydrogencms/hydrogen/modules/images"
	"github.com/hydrogencms/hydrogen/modules/sqlite"
)

func useModules(h *hydrogen.Builder) { h.Use(sqlite.Module(), images.Module()) }
```

The output is deterministic. Import names come from the last path element (without a `/vN` suffix or a
`hydrogen-` prefix); catalog modules claim theirs first and later clashes get a number (`images2`). The file is
written only when it changes. Commit it: a fresh checkout builds with plain `go build`.

A new project's `hydrogen.go` calls `useModules(h)` first in `configure`, then registers hooks, access rules and
endpoints. Modules registered by hand coexist with this: `h.Use` can be called any number of times. A project
without `hydrogen.yaml` is left alone by every command (`generate` skips the file), so existing hand-written
`h.Use(sqlite.Module(), …)` code keeps working. To move such a project to `hydrogen.yaml`:

```sh
hydrogen modules init sqlite postgres pages
```

This creates the two files and prints the `h.Use` calls in your Go files. Call `useModules(h)` at the start of
`configure` and delete the hand-written registrations of the same modules (a module registered twice fails at
startup); your code is never rewritten for you.

## Third-party modules

A third-party module is any Go package with `func Module() kernel.Module`.

```sh
hydrogen add github.com/acme/hydrogen-stripe            # go get …@latest unless go.mod already has it
hydrogen add github.com/acme/hydrogen-stripe@v1.4.0     # go get …@v1.4.0
```

For a module in a local directory, point `go.mod` at it first, then add it by path:

```sh
go mod edit -require=example.com/stripe@v0.0.0 -replace=example.com/stripe=../stripe
hydrogen add example.com/stripe
```

Catalog modules are versioned with the core and take no `@version`. The module's own config goes under
`modules.<name>` in `config/app.yaml`, where `<name>` is what its `Name()` returns. See
[module versions](module-versions.md) for compatibility checks and how to read the versions at runtime.
